# Архитектура моделей и редактора Striped Skins

Дата исследования: 26 октября 2026. Это исходный аудит до реализации вертикального среза.
Текущий объём описан в [руководстве среза](model-lab.md), дальнейшая работа — в [плане редактора](editor-roadmap.md).

Исследованы Striped Skins на `ce05186` и соседний MineLittlePony, ветка `1.20.1`, коммит `2398b14a`. В `gradle.properties` референса указаны Minecraft `1.20.1` и Mson `1.9.3+1.20.1`.

## Рекомендация

Сохранить Three.js, React Three Fiber, Zustand и существующий standalone viewer. Заменить вручную описанные JSX-поверхности на граф именованных частей, собранный из подготовленных данных MineLittlePony. Данные геометрии и правила изменения модели должны быть отделены от React и от изменяемого документа скина.

Основной путь: **Mson JSON + ограниченный перенос поведения Java → генератор при разработке/сборке → собственное нормализованное описание модели → Three.js**.

Готовить модели заранее полезно. Выбирать FBX как основной источник или формат доставки для этой задачи оснований нет. Если понадобится стандартный формат готовых мешей, использовать GLB вместе с метаданными частей. Ни FBX, ни GLB сами по себе не реализуют правила рас, пропорций, аксессуаров и редактирования текстуры.

## 1. Текущая архитектура

| Уровень                   | Текущее устройство                                                                          | Оценка                                                            |
| ------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `app`                     | React Router, загрузка скинов, proxy, URL и UI сравнения                                    | Подходит для сохранения                                           |
| `packages/api`            | `PonySkin`, DOM/canvas-адаптер `ImageTransformer`, чтение служебных пикселей                | Можно сохранить публичный фасад, выделить чистый codec и документ |

| Модель                    | `PonyImplementation` → компоненты частей → `Box`/`Plane`; размеры и UV записаны прямо в TSX | Главный участок переработки                                       |

Режим `frameloop="demand"` уже есть. Его следует сохранить: кадр нужен при изменении камеры, модели или текстуры, а также пока работает анимация. Наличие R3F не является причиной текущих ограничений.

Не следует считать наличие значения в API полноценной визуальной поддержкой.

### Издержки текущего рендера

`Box` создаёт шесть `Plane`. Каждый `Plane` создаёт отдельные `mesh`, геометрию и материал. Даже обычный куб становится шестью отдельными объектами отрисовки; переиспользование одного материала само по себе не объединит эти объекты в один draw call. Тело и хвост тоже разбиты на множество отдельных поверхностей.

В `Plane` новый `PlaneGeometry` создаётся в теле React-функции, а в `PonyModel` там же создаётся новый `CanvasTexture`. Повторный React-render может повторять эти выделения. Для текстуры нет явно заданного владельца и освобождения, а её фильтры выставляются в каждом `Plane`. Это недостаточная модель управления ресурсами для интерактивного редактора; фактический рост GPU-памяти следует измерить отдельно.

Объединять нужно поверхности **внутри одной независимо управляемой части с одинаковым материалом и режимом рендера**. Например, шесть сторон головы можно сделать одной геометрией; левое ухо и голову объединять не нужно, если пользователь должен скрывать их независимо. Также нельзя объединять неподвижные поверхности с независимо анимируемыми сегментами хвоста.

Числа FPS, времени загрузки и общей экономии draw calls в этом исследовании не измерялись. Вывод об избыточной дробности основан на структуре кода, а не на профилировании браузера.

## 2. Что является источником истины в MineLittlePony

Геометрия уже доступна в `src/main/resources/assets/minelittlepony/models/entity/`:

- `steve_pony.json` — общий пони;
- `races/steve/*.json` и `races/alex/*.json` — расы и обычные/slim-варианты;
- `components/*.json` — морды, уши, крылья, хвосты, плавники и другие компоненты;
- `gear/*.json` — аксессуары.

Это Mson, а не простые независимые описания кубов: есть наследование `parent`, локальные выражения, ссылки `#...`, импорты, planar-геометрия, зеркалирование, раздувание `dilate`, pivot и rotation. База `steve_pony.json` наследует `mson:steve`, которого в ресурсах самого мода нет. Для корректного импорта нужны соответствующие ресурсы и семантика закреплённой версии Mson.

Часть результата определяется Java:

| Источник                                                                                            | Что оттуда переносить                                                               |
| --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `api/pony/meta/TriggerPixel.java`, `Race`, `Sizes`, `Gender`, `Wearable`, `TailShape`, `TailLength` | Контракт метаданных скина                                                           |
| `client/model/ModelType.java`                                                                       | Соответствие расы модели, обычные/slim-варианты, реестр аксессуаров                 |
| `client/transform/PonyTransformation.java`                                                          | Пропорции частей для каждого размера и зависимость от позы                          |
| `client/render/EquineRenderManager.java`                                                            | Применение общего масштаба                                                          |
| `client/model/AbstractPonyModel.java`, `entity/race/*`                                              | Сборка, трансформации частей, видимость и особенности рас                           |
| `client/model/part/*`                                                                               | Формы и движение хвоста, сложенные/раскрытые крылья, морда, уши                     |
| `client/model/gear/*`, `client/render/entity/feature/GearFeature.java`                              | Крепление аксессуаров, высоты стека, положение сумок                                |

Просто загрузить JSON или автоматически экспортировать его в FBX недостаточно: Java-реализации, названные в `implementation`, не превратятся в поведение браузера автоматически.

### Размеры

Шесть пользовательских пресетов: NORMAL, FOAL, YEARLING, TALL, LANKY, BULKY. UNSET — служебное состояние, которое не нужно показывать седьмым телосложением.

Нужны одновременно общий масштаб из `Sizes` и отдельные трансформации из `PonyTransformation`. Например, FOAL дополнительно увеличивает голову в 1.3 раза и укорачивает ноги по Y до 0.81, BULKY расширяет тело, LANKY вытягивает корпус и меняет его ширину. FOAL и YEARLING имеют одинаковый базовый scale 0.6, но разные пропорции. Один `group.scale` этого не воспроизводит.

Параметры камеры и тени из `Sizes` не являются размерами меша. Пользовательский общий масштаб мода также следует отличать от пресета телосложения. Для сравнения двух моделей камера должна кадрировать всю сцену, сохраняя относительный размер пони.

### Аксессуары и комбинации

В скине каждый из трёх каналов пикселя `(1,1)` задаёт один ID аксессуара. Это до трёх различных ID, а не битовая маска. Повтор ID не добавляет вторую копию. Восемь ненулевых значений: crown, muffin, hat, antlers, saddlebags left/right/both, stetson. BOTH представляет две физические сумки одним ID.

В редакторе нельзя молча сохранять больше трёх ID в этот пиксель. Расширенные наборы можно разрешить в проектном формате с явным обозначением, что обычный PNG их полностью не передаст. В моде есть и дополнительные источники метаданных, но их поддержка выходит за пределы одного скина PNG.

У короны, маффина, stetson и witch hat есть `IStackable` и собственные высоты. В `GearFeature` порядок обхода псевдослучайный и зависит от UUID сущности; порядок RGB-каналов не задаёт порядок шляп. Для редактора нужен стабильный порядок предпросмотра. Для точного воспроизведения конкретного игрока потребуется отдельный контекст с UUID и воспроизведением порядка референса.

Сумки крепятся к BODY; одиночные и парные варианты имеют разные смещения и ремень. При раскрытых крыльях сумки опускаются. Нельзя без проверки считать LEFT+RIGHT эквивалентом BOTH. Legacy-сумки могут брать текстуру из скина игрока; для бэтпони и чейнджлингов действуют другие правила, а у крыльев есть специальный legacy-вариант. Стандартные текстуры других аксессуаров обычно отдельные; witch hat ссылается на ресурс Minecraft.

Дата, имя сущности и игровые настройки тоже могут влиять на вид аксессуаров. В редакторе предлагается явный стабильный контекст предпросмотра, без неявных изменений от текущей даты.

## 3. Предлагаемые границы системы

```text
upstream MineLittlePony + Mson, закреплённые версии
                  ↓ tools/import-mlp-models
        generated model definitions + provenance
                  ↓
SkinDocument → metadata codec → resolveAppearance(metadata, previewOverrides)
     ↓                                  ↓
2D texture view                 model assembler + pose rules
     ↑                                  ↓
     └──── brush/history ← hit UV ← Three.js / R3F viewer
```

### A. Документ скина и codec

`SkinDocument` владеет изменяемыми RGBA-пикселями, шириной/высотой, исходным форматом и revision. Canvas — адаптер для отображения и загрузки в GPU; renderer не должен владеть единственной копией документа. Декодирование метаданных и работа с пикселями должны быть доступны без DOM, чтобы их можно было проверять на маленьких буферах.

`PonySkin.fromUrl` можно оставить совместимым фасадом загрузки. Zustand хранит ссылки на документы, их версии, настройки и состояние UI. Не следует создавать новое дерево модели или новый `PonySkin` для каждого движения кисти и подписывать всю сцену на полный массив пикселей.

Нужны отдельные понятия:

- `metadata` — данные, действительно закодированные в PNG;
- `previewOverrides` — временный выбор расы, размера, формы и аксессуаров;
- `visibility` — что пользователь скрыл для просмотра/рисования;
- `pose` — статическая поза, раскрытие крыльев, водная форма и т. п.

Изменение предпросмотра не должно переписывать PNG, пока не выполнена команда изменения метаданных. В сравнении два независимо загруженных скина должны иметь независимые изменяемые документы, даже при одинаковом URL: сейчас default/first/second могут ссылаться на один объект `PonySkin`.

### B. Данные моделей

Начать с внутреннего версионированного формата `ModelDefinition`: дерево узлов, стабильные ID, локальные трансформации, faces/cuboids, UV, материал, семантическая часть, attachment points и ссылки на нужные контроллеры поведения. Хранить UV в координатах логического атласа с явным размером; нормализовать их при построении геометрии. Реальная ширина картинки не обязана совпадать с логическими 64 пикселями атласа.

Генератор разрешает Mson-наследование и выражения заранее. Полноценный интерпретатор Mson в браузере не нужен. Неизвестные конструкции и реализации должны давать диагностическую ошибку генерации, а не незаметно исчезать из модели.

Для первого этапа нужен только используемый этими моделями поднабор Mson. Его семантику необходимо сверить с Mson 1.9.3, особенно переопределения children, ссылки на части, UV при `dilate` и зеркалирование. Если это окажется сложнее ожидаемого, альтернативой будет инструмент экспорта уже разрешённого дерева ModelPart из среды мода; размеры и динамическое поведение всё равно остаются отдельным слоем.

В результат включать SHA источника, версию Mson, версию генератора и таблицу соответствия upstream-имён стабильным ID редактора. Сгенерированные данные должны поставляться в npm/standalone bundle: у пользователя библиотеки не должно быть зависимости от соседнего checkout или Java.

### C. Сборщик и поведение

`resolveAppearance` выбирает определение расы и slim-варианта, применяет размер, пол/морду, длину/форму хвоста и аксессуары. Применение порядка матриц должно соответствовать модулю-референсу. Простая переносимая иерархия головы и тела сама по себе не гарантирует совпадения с Java render stages.

Геометрический граф и логическое дерево частей — разные вещи. В Three.js узлы могут быть раздельными из-за стадий трансформации, но UI должен видеть одну семантическую часть. Например, голова, её второй слой и закреплённые аксессуары могут получать связанные трансформации, оставаясь независимо скрываемыми.

Для кубических моделей достаточно обычных `Group`/`Mesh` с pivots. `SkinnedMesh`, общий скелет, morph targets и универсальный animation engine не являются обязательным первым шагом. Локальные контроллеры крыльев, хвоста и позы можно добавлять поверх тех же узлов, изменяя их трансформации без React-state на каждом кадре.

Морскую форму нужно выбирать явно в предпросмотре. В игре выбор зависит от воды и наличия дополнительной seapony-текстуры; один исходный PNG не описывает весь игровой контекст. Наличие гиппогрифа в реестре не означает, что водную форму можно всегда вывести только из цвета расы.

### D. Renderer

- Собирать один `BufferGeometry` на независимо управляемую часть и совместимый материал; сохранять плоские нормали и UV-швы.
- Кэшировать неизменяемые геометрии по определению/варианту. Создавать отдельные Object3D и контроллеры для каждого экземпляра; две пони не должны делить изменяемые transforms.
- Переиспользовать материалы в пределах совместимой текстуры, стороны и alpha-режима. Материалы разных редактируемых скинов нельзя случайно связать общей изменяемой `map`.
- Выделять GPU-текстуру один раз на документ и renderer-контекст; менять её содержимое и `needsUpdate`, явно освобождать ресурсы. Общий кэш должен иметь одного владельца либо учёт ссылок.
- Задавать фильтры, цветовое пространство и ориентацию текстуры централизованно. Для pixel art использовать nearest; решение об alpha cutout и настоящем blending принимать по нужному визуальному результату. Механически убирать полупрозрачность везде нельзя.
- При переключении видимости менять состояние существующих частей. Скрытые части также исключать из списка кандидатов для picking.
- Оставить demand-render; после изменения текстуры, видимости или imperative transforms вызывать `invalidate`. Продолжать кадры только при активной анимации или движении камеры.

Не объединять всю пони в один меш ради минимального числа draw calls: это усложнит индивидуальное скрытие и анимации. Не начинать с instancing, BVH, WebGPU или пользовательских шейдеров; для одной-двух таких моделей их необходимость сначала должна появиться в профиле.

## 4. Выборочное скрытие

Стабильные ID должны охватывать каждую доступную семантическую часть и, при необходимости, её подчасти: череп, морду, левое/правое ухо, рог, гриву/второй слой головы, шею, корпус, каждую ногу и её внешний слой, левое/правое крыло, сегменты хвоста, плавники, отдельные аксессуары и стороны сумок.

Упрощённое правило: `effectiveVisible = availableInVariant && allowedByPose && userVisible && parentPolicy`. Пользовательская видимость не должна затираться очередным animation tick. Доступность частей пересчитывается при смене расы, но устойчивые ID сохраняют осмысленные настройки.

В UI нужны различимые операции «скрыть только геометрию этой части», «скрыть ветку» и «изолировать». Нельзя прятать transform-группу черепа, если пользователь хотел оставить отдельно видимыми уши и шляпу. Поэтому transform-группа может оставаться активной, а её собственные mesh — отключаться. Групповые переключатели работают поверх реестра частей.

## 5. Подготовка к рисованию по модели и текстуре

Обе поверхности редактируют один `SkinDocument` и вызывают один brush/history engine. 2D-вид переводит экранную позицию в пиксель с учётом zoom/pan; 3D-вид переводит попадание луча в UV и затем в пиксель того же документа.

Для простой текстуры без UV-transform, с выбранной ориентацией V снизу вверх:

```text
x = clamp(floor(u * width), 0, width - 1)
y = clamp(floor((1 - v) * height), 0, height - 1)
```

Конкретное преобразование должно быть единым контрактом с `flipY`, импортом GLB и отображением 2D. На границах UV-островов нужны правила выбора пикселя и ограничения текущей гранью, чтобы кисть не попадала в соседний участок атласа. Варианты с texture transforms сначала приводят hit UV к координатам документа.

Нужны `partId`, `surfaceId`, `textureId` и соответствие треугольников исходным граням. Их следует сохранять при объединении поверхностей. Это позволяет показывать выделение в 2D и рисовать только по выбранной части/слою. Фиксированные текстуры аксессуаров должны отличаться от редактируемой текстуры скина: попадание в шляпу не должно менять случайные пиксели PNG пони.

Особенности, которые стоит заложить заранее:

- Raycast попадает в геометрию даже в прозрачной области текстуры. Для обычного выбора видимой поверхности нужно проверять alpha и искать подходящее следующее попадание; для добавления новых пикселей на пустом внешнем слое нужен отдельный режим выбора активного слоя, который допускает такое попадание.
- Проверять видимость и доступность явно, а не полагаться на `Object3D.visible` как универсальный фильтр raycaster.
- Кисть интерполирует движение в пределах одной поверхности; при переходе на другую грань нельзя просто проводить длинную прямую между несмежными UV-островами. Сначала можно завершать такой сегмент штриха, позже добавить перенос через известное соседство граней.
- Повторяющиеся и зеркальные UV означают, что один пиксель меняет несколько поверхностей. Это свойство скина нужно показывать, сохраняя совместимую развёртку.
- Один завершённый штрих — одна операция undo/redo. Хранить изменённые пиксели до/после, а не создавать новый PNG на каждый pointermove.
- На время рисования замораживать анимацию и отключать вращение камеры; поддержать pointer capture и завершение/отмену штриха.
- Обновлять canvas/GPU не чаще одного раза за кадр. Для маленького скина обычная полная загрузка текстуры после пакета изменений — разумная отправная точка; partial GPU uploads нужны лишь после измерений на HD.
- Служебные пиксели защищать от обычной кисти и менять отдельными командами метаданных; предусмотреть явный доступ к ним в расширенном 2D-режиме. Во время такого штриха откладывать перестройку модели до завершения, чтобы поверхность не исчезала под кистью.

Для 64×32 и HD нужен явный этап нормализации и сохранённая информация об исходном формате. Преобразование legacy→modern должно повторять vanilla-правила плюс перенос крыльев MLP. Возможность обратного экспорта 64×32 ограничена: независимые новые области современного скина в старом формате не сохранятся. Политика экспорта должна показывать это пользователю.

## 6. FBX, GLB или собственные данные

| Вариант                                  | Преимущества                                                                     | Ограничения в этом проекте                                                                               | Решение                                               |
| ---------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| Текущий ручной JSX                       | Простая точечная правка уже имеющихся частей                                     | Дублирование upstream, много объектов, трудно обеспечивать паритет всех рас                              | Использовать лишь как временный renderer при миграции |
| Отдельные FBX                            | Удобны при существующем DCC-процессе моделирования                               | Дополнительное преобразование Mson; нужны метаданные и поведение; расширение файла не снижает draw calls | Не вводить как основной путь                          |
| GLB с именованными узлами и метаданными  | Стандартный контейнер готовой геометрии, иерархии и анимаций; загрузчик Three.js | Не содержит автоматически MLP-правила, требует аккуратного экспорта UV/ID и отдельного assembler         | Возможный будущий выход генератора                    |
| Нормализованный JSON/TS + BufferGeometry | Прямая связь с Mson, контроль частей/UV, удобные автоматические проверки         | Нужен небольшой собственный формат и генератор                                                           | Предпочтительный первый путь                          |

FBX/GLB не мешают рисованию по UV. Их основной недостаток здесь — дополнительный слой поддержки без устранения предметной логики. Один файл на каждую комбинацию расы × размера × аксессуаров создавать не нужно. Размеры и аксессуары должны компоноваться; физически уникальную геометрию можно хранить отдельными вариантами и загружать по необходимости.

При появлении художника и ручных анимаций разумен процесс Blender/Blockbench → GLB → тот же assembler. При оптимизации экспорта нельзя объединять части, удалять значимые имена или перепаковывать UV вопреки контракту PNG. Внешняя текстура документа назначается после загрузки модели.

## 7. Порядок миграции

1. **Контракт совместимости.** Закрепить upstream SHA и Mson, согласовать состояние предпросмотра: обычная поза, global scale, snuzzles, крылья, морская форма и порядок аксессуаров. Подготовить диагностические скины с подписанными/цветными UV-гранями и образцы всех рас. Уточнять паритет по исходникам и изображениям из мода, а не только по старому viewer.
2. **Новый codec и документ.** Исправить Human/fallback и alpha служебных пикселей, выделить buffer-based codec, сохранить публичный фасад API. Добавить независимость документов в сравнении и явные preview overrides. Создать round-trip проверки метаданных и PNG.
3. **Вертикальный срез нового renderer.** Перенести Earthpony обычную/slim, реестр частей, GPU lifecycle, общий материал и объединение поверхностей внутри частей. Проверить старый формат и первый штрих на модели с появлением пикселя в 2D. Не откладывать проверку рисования до окончания всех рас: это проверка архитектуры UV и документа.
4. **Размеры и расы.** Перенести все шесть пропорций; далее рог/крылья и оставшиеся уникальные формы. Все формы хвоста и folded/extended-крылья должны попасть в ту же систему поведения. Для Human использовать отдельную модель/ветку, не пони без рога.
5. **Аксессуары.** Перенести восемь ID, текстуры, крепления, стек и взаимодействие сумок с крыльями. Добавить просмотр комбинаций и ограничения экспорта в PNG.
6. **Полноценный редактор.** Кисть 2D/3D, выбор слоёв, история, zoom, импорт/экспорт. Делать отдельным необязательным пакетом, чтобы standalone viewer не тянул UI рисования и историю.

Возможная структура: сохранить `packages/api` для документа/codec и совместимого фасада; добавить `packages/models` для сгенерированных определений и правил сборки; оставить `packages/viewer` владельцем Three.js; `packages/editor` добавить только при реализации редактирования. Генератор разместить в `tools/import-mlp-models`. Дополнительное дробление на множество пакетов сейчас не требуется.

Существующие тесты проверяют переходы сравнения и URL, но не геометрическое соответствие MLP. Для нового renderer нужны:

- данные: все расы, шесть размеров, обычные/slim-варианты, прозрачные/неизвестные trigger pixels, все формы/длины хвоста;
- изображения: базовая сетка 12 рас × 6 размеров × 2 варианта ширины = 144 комбинации, с детерминированной позой и камерой; дополнительно края матрицы по морде/хвостам/крыльям и совместным аксессуарам;
- комбинации: каждый аксессуар отдельно и все кодируемые наборы до трёх ID на уровне resolver; визуально отдельно проверять стек головных аксессуаров и конфликтующие варианты сумок;
- взаимодействие: скрытие каждой части влияет и на рисунок, и на picking; штрих из 3D отражается в 2D, undo восстанавливает точные пиксели, round-trip PNG сохраняет метаданные; рисование первого скина не меняет второй;
- ресурсы: `renderer.info.render.calls`, geometry/texture counts, время кадра и GPU-память при многократной смене скина, размеров, сравнения и mount/unmount. Проверять стабилизацию после прогрева с учётом ограниченного кэша.

## 8. Выявленные расхождения codec, которые нельзя потерять при переносе

`Race.fromPixel` в текущем API возвращает Earthpony для неизвестного цвета; Human зарегистрирован с искусственным значением `"none"`, поэтому из обычного RGBA-пикселя не выбирается. В MLP `TriggerPixel.RACE` имеет default Human и цвет Human `0x000000`. Режим принудительного превращения людей в пони — отдельная настройка мода, а не причина менять базовый decoder.

MLP читает enum-значения и wearable flags только при alpha служебного пикселя 255; текущие `fromPixel` отбрасывают alpha и распознают RGB независимо от прозрачности. `Snout` в API — практическая интерпретация `Gender` референса; для полноценного паритета лучше хранить исходный enum, а представление морды вычислять отдельно.

В показанном `TriggerPixel.java` координаты служебных пикселей фиксированы. Не следует автоматически умножать их на HD scale по аналогии с UV: проверять нужно фактический контракт загрузки HD и референсные изображения. Нормализованные UV и физические координаты служебных пикселей относятся к разным контрактам.
